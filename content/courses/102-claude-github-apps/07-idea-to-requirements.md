## このレッスンのゴール

- アプリを作る前に決めておくべきことを挙げられる
- 要件定義書（REQUIREMENTS.md）の構成を読める・書ける
- 「最初は小さく作る（MVP）」の理由を説明できる

## いきなり「作って」は遠回り

> オンラインショップを作って

これだけで頼むと、AI は **自分で想像して** 決めます。会員登録は要る？ 決済は？ 在庫は？ スマホ向け？ …想像が外れると、作り直しになります。
**決めることを先に決めてから頼む** 方が、結果的にずっと速く進みます。

## 要件定義書：作るものの設計図

fashion_news のリポジトリには `REQUIREMENTS.md` がありました。あれが要件定義書の実例です。中身はこういう構成でした。

| 見出し | 書くこと | fashion_news の例 |
|---|---|---|
| 1. 目的 | 何のために作るか | 毎朝、ファッションニュースを自動で集めて Notion にまとめる |
| 2. 機能要件 | 何ができるか | 情報源・ジャンル分け・重複除去・件数・出力の形 |
| 3. 非機能要件 | どう動くか（速さ・時刻・安全） | 1 日 2 回、GitHub Actions で。秘密は Secrets に |
| 4. 構成案 | ファイルの分け方 | fetch.py・classify.py・dedupe.py・notion.py |
| 5. 対象外 | **今回やらないこと** | 要約、海外メディア、AI による分類 |
| 6. 未確定事項 | まだ決まっていないこと | チェックボックスで管理 |

特に大事なのは **「5. 対象外」** と **「6. 未確定事項」** です。やらないことを書くと範囲が膨らまず、決まっていないことを書くと AI が勝手に決めずに聞いてくれます。

## AI と一緒に要件を作る

要件定義書を、ゼロから自分で書く必要はありません。**AI に質問してもらいながら作る** のがおすすめです。

> 友達 3 人で使う、ポップアップ出店の準備用アプリを作りたい。
> いきなり作らずに、まず要件定義書（REQUIREMENTS.md）を一緒に作りたいので、決める必要があることを質問して。

AI が「データは全員で共有する？」「ログインは必要？」「スマホで使う？」などを聞いてくれるので、答えていくと要件がまとまります。最後に「この内容で REQUIREMENTS.md を書いて」と頼みます。

## MVP：最初は小さく作る

**MVP**（Minimum Viable Product）は、「使えるけれど、いちばん小さい版」のことです。

| | 全部入り | MVP |
|---|---|---|
| オンラインショップ | 会員・決済・在庫・レビュー・管理画面… | 商品一覧と、注文フォーム（メールで届く）だけ |
| popup2027 | ログイン・通知・権限・写真の保存先… | タスクと予定を共有できるだけ |

MVP から始める理由：

- **早く動くものが見られる**：実際に使うと、本当に必要なものが分かる
- **確かめられる量で進む**：一度に大きく作ると、どこが悪いか分からない
- **作り直しが小さい**：想像が外れても、捨てるものが少ない

要件定義書の「機能要件」を、**MVP に入れるもの** と **あとで足すもの（Issue にしておく）** に分けておくと、その後の進め方がそのまま決まります。

## 技術を決めるときの質問

要件が決まったら、「何で作るか」を AI と相談します。次の質問に答えると、選択肢が絞れます。

| 質問 | 答えによって変わること |
|---|---|
| 何人が使う？ 自分だけ？ | 自分だけなら、データはパソコンの中でもよい |
| データを共有する？ | 共有するなら、データベース（Firebase などの BaaS）が必要 |
| ログインは必要？ | 必要なら、認証サービスを使う（バックエンドコース「認証と認可」） |
| お金・個人情報を扱う？ | 扱うなら、既製品のサービスに任せる部分を増やす |
| 決まった時刻に動かす？ | GitHub Actions の定時実行など |
| どこで見る？ | ブラウザ・スマホ・Notion・LINE … |

迷ったら、**「いちばん簡単に作れて、後から作り変えられる方法を提案して」** と頼みましょう。

```quiz
? 要件定義書に「対象外（やらないこと）」を書いておく一番の理由は？
- 文書を長くするため
+ 範囲が膨らむのを防ぎ、AI が頼んでいない機能まで作らないようにするため
- GitHub のルールだから
> やらないことが決まっていると、作るものがはっきりします。

? MVP の考え方として正しいのは？
+ 使える最小の版を先に作り、使いながら必要なものを足していく
- 必要になりそうな機能を最初に全部作る
- デザインだけ先に完成させる
> 早く動くものを見て、確かめながら育てるのが基本です。

? 要件がまだぼんやりしているとき、AI へのよい頼み方は？
- 「いい感じに全部作って」
+ 「決める必要があることを質問して。一緒に要件定義書を作りたい」
- 何も言わずにコードだけ頼む
> 質問してもらいながら要件を固めると、作り直しが減ります。
```
