## このレッスンのゴール

- Claude に伝わる Issue を書ける
- 「Issue #3 をやって」と頼んだときに何が起きるか説明できる
- PR の説明の `Closes #3` の意味が分かる

## Issue＝やることを 1 枚ずつ書いた付箋

チャットで頼むと、会話が終われば内容は流れてしまいます。**Issue に書いておくと、やることが GitHub に残り、番号で呼べます**。
アプリ作りの「やることリスト」を Issue で管理しておくと、

- 何が終わって、何が残っているか一目で分かる
- 新しい会話でも「Issue #3 をやって」の一言で伝わる
- 誰が・いつ・どう直したかが、Issue と PR につながって残る

## 伝わる Issue のテンプレート

AI と開発するコース「伝わる頼み方」の 4 要素を、そのまま Issue の形にします。

```markdown
## 目的
商品一覧で、在庫切れの商品が分かるようにしたい

## 今の状態
在庫が 0 でも、他の商品と同じ見た目で表示されている

## やってほしいこと
- 在庫 0 の商品に「在庫切れ」のラベルを付ける
- 在庫切れの商品は「カートに入れる」ボタンを押せないようにする

## やらないこと
- 在庫の数の管理画面は今回は作らない

## 完成の条件
- 在庫 0 の商品で、ラベルが出てボタンが押せないことを画面で確認できる
- 既存のテストが通る
```

| 見出し | ポイント |
|---|---|
| 目的 | なぜやるのか。AI が細かい判断をするときの手がかりになる |
| 今の状態 | バグなら「どうすると・どうなる」（再現手順） |
| やってほしいこと | 箇条書きで具体的に |
| やらないこと | AI が「ついでに」広げすぎるのを防ぐ |
| 完成の条件 | 確かめ方。これが無いと「できました」の判断がぶれる |

**1 つの Issue には 1 つのこと** を書くのがコツです。「あれもこれも」を 1 つにすると、PR が大きくなってレビューできなくなります。

## 「Issue #3 をやって」で起きること

```text
① Claude が gh で Issue #3 を読む
② 作業用のブランチを作る（例：fix/3-out-of-stock-label）
③ コードを書き換え、動かして・テストして確かめる
④ コミットして、GitHub に push
⑤ PR を作る。説明に「Closes #3」と書く
⑥ あなたが PR の差分を読む（AI と開発するコース「差分を読んでレビューする」）
⑦ 問題なければマージ → Issue #3 が自動で閉じる
```

⑤ の **`Closes #3`**（または `Fixes #3`）は特別な書き方で、PR が main にマージされた瞬間に、Issue #3 を自動で「完了」にしてくれます。

④ と ⑤ は GitHub に影響する操作なので、Claude はあなたの了承を取ってから行います（レッスン 3）。

## よく使う gh のコマンド

```bash
gh issue list                       # 開いている Issue の一覧
gh issue view 3                     # Issue #3 の中身
gh issue create --title "..." --body "..."   # Issue を作る
gh pr create --fill                 # 今のブランチから PR を作る
gh pr view 5 --web                  # PR #5 をブラウザで開く
gh pr checks 5                      # PR #5 の自動テストの結果
```

Claude がこれらを実行していたら、「Issue を読んでいる」「PR を作っている」と読めます。

## ラベルとマイルストーン

| 機能 | 使い方の例 |
|---|---|
| ラベル | `bug`（不具合）・`enhancement`（機能追加）・`good first issue`（簡単なもの） |
| マイルストーン | 「v1.0 公開まで」のように、Issue を目標ごとにまとめる |
| Projects | Issue をカンバン（未着手・進行中・完了）で並べる |

小さな個人のアプリなら、まずは **Issue ＋ ラベル 2〜3 個** で十分です。

```quiz
? Issue に「やらないこと」を書いておく一番の理由は？
+ AI が頼んでいない範囲まで広げて変更するのを防ぐため
- Issue を長くするため
- GitHub のルールで必須だから
> 範囲がはっきりすると、PR も小さくレビューしやすくなります。

? PR の説明に `Closes #3` と書くと、何が起きる？
- PR #3 が閉じる
+ その PR が main にマージされたとき、Issue #3 が自動で閉じる
- Issue #3 が削除される
> Issue と PR が自動でつながり、完了の記録が残ります。

? 「ログイン機能と、商品の並べ替えと、デザイン変更」を頼みたい。Issue はどう書く？
- 1 つの Issue にまとめる
+ 3 つの Issue に分ける
> 1 Issue 1 テーマにすると、PR も小さく、確認もしやすくなります。
```
