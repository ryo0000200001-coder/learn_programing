## このレッスンのゴール

- 本番で問題が起きたとき、何から順にやるかを説明できる
- ロールバック・ログ・監視・バックアップの役割を説明できる
- 「戻せる」状態を、公開する前から用意しておく理由が分かる

## 問題が起きたときの順番

```text
① 気づく     ……  監視・アラート、利用者からの連絡
② 被害を止める ……  まず戻す（ロールバック）。原因探しは後
③ 原因を探す   ……  ログ・エラー・直前の変更
④ 直す        ……  修正 → テスト → もう一度公開
⑤ ふり返る     ……  なぜ起きた？次はどう防ぐ？
```

いちばん大事なのは ② です。**原因が分からなくても、直前の状態に戻せば、多くの場合すぐに直ります**。本番が壊れたまま原因を探すと、その間ずっと利用者が困ります。

## ロールバック：前の版に戻す

| 公開の方法 | 戻し方 |
|---|---|
| Git の push で自動公開（このサイト、Vercel など） | 原因のコミットを `git revert` して push（ターミナルと Git のコースのレッスン 7） |
| Vercel・Netlify・Cloudflare Pages・Render | 管理画面の「過去のデプロイ」から、前の版を選んで「Rollback」「Promote」 |
| Cloudflare Workers | `npx wrangler rollback`（前の版に戻す） |
| Docker のイメージ | 前のタグ（`hello-api:1.4.2`）のイメージで起動し直す |

⚠️ **データベースの変更（マイグレーション）は、コードと一緒に戻らない** ことに注意します。列を消すマイグレーションを本番で実行した後にコードだけ戻すと、古いコードが「無い列」を使おうとして、さらに壊れます。
そのため、列を消す・名前を変えるような変更は、**① 新しい列を足す → ② コードを新しい列に切り替える → ③ 古い列を消す** のように、何回かに分けて安全に進めるのが定番です。

## ログを読む

ログは、プログラムが「何をしたか」を書き残した記録です（バックエンドコースのレッスン 10）。

```text
2026-11-21T08:12:03Z INFO  GET /tasks 200 12ms
2026-11-21T08:12:05Z ERROR POST /orders 500 user_id=42
Traceback (most recent call last):
  ...
  File "/app/orders.py", line 31, in create_order
    total = price * qty
TypeError: unsupported operand type(s) for *: 'NoneType' and 'int'
```

| 読み方 | この例では |
|---|---|
| 時刻（多くは UTC） | 日本時間では 17:12。「何時ごろから？」と照らし合わせる |
| レベル | `ERROR` を探す。`INFO` は普通の記録 |
| どのリクエスト | `POST /orders` で 500 |
| エラーの最後の行 | `price` が `None` だった。値段の無い商品が原因かも |
| いつから？ | 最初の `ERROR` の時刻と、**直前のデプロイの時刻** を比べる |

| どこで見る | |
|---|---|
| PaaS・サーバーレス | 管理画面の「Logs」。Workers は `npx wrangler tail` で流れてくるログを見られる |
| Docker | `docker logs コンテナ名`（レッスン 6） |
| GitHub Actions | Actions のタブ（レッスン 7） |

⚠️ ログに **パスワード・トークン・個人情報** を書かないこと。ログは多くの人が見られる場所に、長く残ります。

## 監視：利用者より先に気づく

| 種類 | 何を見る | 道具の例 |
|---|---|---|
| **死活監視** | サイトが応答するか（数分ごとにアクセスしてみる） | UptimeRobot、Better Stack、Cloudflare のヘルスチェック |
| **エラー監視** | 起きた例外を集めて、まとめて知らせる | Sentry |
| **数値の監視** | リクエスト数・エラー率・応答時間・CPU・メモリ | 各クラウドの管理画面、Grafana |
| **料金の監視** | 請求額 | 予算のアラート（レッスン 5） |

```python
@app.get("/health")
def health():
    conn.execute("SELECT 1")        # データベースにもつながるか確かめる
    return {"status": "ok"}
```

死活監視のために、**「元気かどうか」だけを返す入口**（ヘルスチェック）を作っておくのが定番です。

アラートは **多すぎても少なすぎてもいけません**。毎日何十通も届くと、本当に大事な知らせを見落とします。「利用者が困っている」ときだけ鳴るようにします。

## バックアップ：最後の砦

コードは Git に全部残っていますが、**利用者のデータは Git にはありません**。データベースが壊れた・間違って消した、に備えるのがバックアップです。

| 確認すること | |
|---|---|
| 自動で取られているか | 多くのクラウドのデータベースには自動バックアップがある。無料プランでは無い・短いことも |
| どこまで戻れるか | 毎日 1 回？任意の時点（D1 の Time Travel など）？何日前まで？ |
| **戻せることを確かめたか** | 一度も戻したことのないバックアップは、本当に使えるか分からない。試しに別の場所に戻してみる |
| 同じ場所に置いていないか | サービスごと使えなくなったときのために、別の場所にもコピー |

## ふり返り：同じことを起こさない

直ったら、**誰かを責めるのではなく、仕組みを直す** ためのふり返りをします。

```text
何が起きた？   ：17:12〜17:40、注文ができなかった
原因は？       ：値段の無い商品を登録できてしまい、計算で None になった
なぜ防げなかった？：データベースに NOT NULL が無かった。テストにも無かった
次の対策       ：price に NOT NULL と CHECK を追加（データベース設計のコース）
                テストに「値段の無い商品」のケースを追加
                エラー監視を入れて、5 分以内に気づけるように
```

このコースのあちこちで学んだこと（制約・テスト・ログ・監視）は、こうして **事故の後に、少しずつ足されていく** ものでもあります。

## AI に手伝ってもらうとき

本番の問題を AI に相談するときは、次をそろえて伝えると、的外れな答えが減ります（AI と開発するコースの「伝わる頼み方」）。

- **いつから** 起きているか、直前に何を変えたか（デプロイの時刻・PR）
- **エラーのログ**（秘密や個人情報は伏せる）
- 手元では再現するか
- すでに試したこと

⚠️ AI が「本番のデータベースで、この SQL を実行してください」と言ってきたら、**バックアップがあるか確かめてから**、まずは手元やステージングで試します。

```quiz
? 公開した直後から注文ができなくなった。原因はまだ分からない。最初にすべきことは？
- ログを全部読んで、原因が分かるまで待つ
+ 直前の版にロールバックして、まず利用者が困らない状態に戻す
- データベースを作り直す
> 被害を止めるのが先です。原因が分からなくても、直前の版に戻せば多くの場合すぐ直ります。原因探しはその後で行います。

? 列を削除するマイグレーションを本番で実行した後、コードだけを前の版に戻した。何が起きうる？
- 何も問題はない
+ 古いコードが、もう無い列を使おうとしてエラーになる
- 削除した列が自動で元に戻る
> データベースの変更はコードと一緒に戻りません。列の削除などは、何回かに分けて安全に進めます。

? バックアップについて、もっとも大事な確認は？
- 毎秒取っているか
+ 実際に戻せることを、一度試して確かめているか
- できるだけ大きなファイルになっているか
> 戻したことのないバックアップは、いざというとき使えるか分かりません。試しに戻してみて確かめます。
```
