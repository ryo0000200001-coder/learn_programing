## Git ＝ セーブポイント付きの作業記録

ゲームのセーブポイントのように、**ある時点のファイルの状態を記録** しておける道具です。
AI が大きく書き換えても、セーブポイントに戻れば元通り。だから **AI に任せる前に Git** が鉄則です。

## 基本の 4 語

| 用語 | 意味 | たとえ |
|---|---|---|
| **コミット（commit）** | 変更を 1 つの記録として保存 | セーブ |
| **ブランチ（branch）** | 本線から分かれた作業の道 | 別のセーブデータで試す |
| **push** | 手元の記録を GitHub などに送る | クラウドにバックアップ |
| **プルリクエスト（PR）** | 「この変更を本線に入れていい？」という提案 | 上司へのレビュー依頼 |

このサイトも、Claude が `claude/...` というブランチで作業してコミットし、GitHub に push しています。

## よく見るコマンド

```bash
git status                 # 今どのファイルが変わっているか
git diff                   # 変更の中身（差分）
git add .                  # 変更をコミットの候補に入れる
git commit -m "説明"       # セーブ
git log --oneline          # セーブの履歴
git switch -c new-feature  # 新しいブランチを作って移る
git push                   # GitHub に送る
```

AI が「これを実行して」と出してきたら、この表と見比べれば何をしているか分かります。

## ⚠️ 取り消せない系のコマンド

| コマンド | 危ない理由 |
|---|---|
| `git reset --hard` | まだコミットしていない変更を **消す** |
| `git push --force` | GitHub 側の履歴を **上書き** する（他人の変更も消えうる） |
| `git clean -fd` | Git が管理していないファイルを **削除** する |

AI がこれらを提案したら、**「何が消えるのか」を確認してから** 実行しましょう。

## コミットメッセージを読む

```text
Add TypeScript course (8 lessons, Lv1-3)
```

AI のコミットは英語の命令形（Add / Fix / Update …）が多いです。
`git log` を読むと「いつ・何のために変えたか」が分かり、プロジェクトの歴史が追えます。

```quiz
? AI に大きな変更を任せる前に Git でコミットしておく理由は？
+ うまくいかなかったときに元の状態に戻せるから
- AI の動作が速くなるから
- コミットしないと AI がファイルを読めないから
> コミットはセーブポイントです。

? 「本線に変更を入れていいか」をレビューしてもらう仕組みは？
- push
- ブランチ
+ プルリクエスト
> PR で差分を確認してから本線（main）に取り込みます。

? 実行前に特に注意すべきコマンドは？
- git status
- git log
+ git reset --hard
> コミットしていない変更が消えてしまいます。
```
