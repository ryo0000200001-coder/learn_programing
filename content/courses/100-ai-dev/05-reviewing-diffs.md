## このレッスンのゴール

- diff の `+` / `-` / `@@` を読める
- AI の変更をレビューするときの観点を挙げられる

## diff の読み方

```diff
--- a/app.py
+++ b/app.py
@@ -10,7 +10,8 @@ def load(path):
     with open(path, encoding="utf-8") as f:
-        data = json.load(f)
+        try:
+            data = json.load(f)
+        except json.JSONDecodeError:
+            data = {}
     return data
```

| 記号 | 意味 |
|---|---|
| `---` / `+++` | 変更前（a）と変更後（b）のファイル |
| `@@ -10,7 +10,8 @@` | 変更前の 10 行目から 7 行分が、変更後は 10 行目から 8 行分になった |
| `-` で始まる行 | **消えた** 行（赤で表示されることが多い） |
| `+` で始まる行 | **増えた** 行（緑） |
| 記号なし | 変わっていない前後の行（場所を示すため） |

この例は「JSON の読み込みに失敗したら空の辞書にする」という変更です。
GitHub のプルリクエストの「Files changed」タブも、同じ形で表示されます。

## AI の変更をレビューする 6 つの観点

1. **頼んだことだけ変わっているか**：関係ないファイルや行まで書き換えていないか
2. **消えた行（-）に大事なものはないか**：チェック処理やコメントが黙って消えていないか
3. **エラーの扱い**：上の例のように `except` で握りつぶしていないか。空の辞書にして本当に大丈夫か
4. **秘密情報**：API キーやパスワードが `+` の行に入っていないか
5. **新しく増えた依存**：`import` や `package.json` に知らないライブラリが増えていないか
6. **テスト**：変更に合わせてテストが追加・修正されているか

## 大きすぎる diff は分けてもらう

数百行の変更を一度にレビューするのは、人間には無理があります。
「1 つの目的ごとにコミットを分けて」「まずこのファイルだけ」と頼むのも立派なテクニックです。

## AI にレビューを手伝わせる

```text
この diff をレビューして。バグ、セキュリティ、頼んでいない変更がないかを重点的に。
```

AI 自身にレビューさせるのも有効です。ただし最終判断は自分で。指摘された内容は、このサイトで学んだ知識で確かめましょう。

```quiz
? diff で `-` で始まる行は？
+ 変更で消えた行
- 変更で増えた行
- エラーのある行
> + が増えた行、- が消えた行です。

? AI の変更をレビューするとき、まず確認したいのは？
+ 頼んだことだけが変わっていて、関係ない所が書き換わっていないか
- 行数が多いかどうか
- コメントが英語かどうか
> AI はついでに他の箇所も変えてしまうことがあります。

? `+ API_KEY = "sk-abc123..."` という行が diff にあった。どうする？
- そのままコミットしてよい
+ 秘密情報なので環境変数などに移してから進める
> 秘密情報をコミットすると、GitHub 経由で漏れる危険があります。
```
