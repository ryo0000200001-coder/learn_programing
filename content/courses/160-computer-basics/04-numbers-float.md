## このレッスンのゴール

- `0.1 + 0.2` がぴったり `0.3` にならない理由を説明できる
- お金の計算で、AI のコードが誤差に対応しているか確認できる
- JavaScript で大きな整数（ID など）が化ける理由が分かる

## 0.1 + 0.2 = 0.30000000000000004

```python
print(0.1 + 0.2)           # 0.30000000000000004
print(0.1 + 0.2 == 0.3)    # False
```

バグではなく、Python・JavaScript・Java など **ほぼすべての言語で同じ結果** になります（Python と JavaScript で実行して確認）。

### 理由：2 進数では 0.1 を正確に書けない

10 進数で 1/3 を書くと `0.3333…` と永遠に続くように、**2 進数（レッスン 2）では 0.1 が永遠に続く** 小数になります。
コンピュータは小数（`float`）を決まった桁数（64 ビット）で持つので、途中で切った **ほんの少しずれた値** を覚えています。

```python
from decimal import Decimal
print(Decimal(0.1))
# 0.1000000000000000055511151231257827021181583404541015625   ← 実際に覚えている値
```

普段は表示のときに丸められて `0.1` に見えますが、計算を重ねるとずれが表に出てきます。

## 対策 1：小数を `==` で比べない

```python
import math
math.isclose(0.1 + 0.2, 0.3)      # True  「ほぼ等しい」で比べる
```

JavaScript では `Math.abs(a - b) < Number.EPSILON` のように書きます。

## 対策 2：お金は小数で計算しない

| 方法 | 例 | 使う場面 |
|---|---|---|
| **整数（いちばん小さい単位）で持つ** | 1980 円は `1980`、12.34 ドルは `1234`（セント） | 多くの決済サービス（Stripe など）が採用 |
| **`Decimal` を使う**（Python） | `Decimal("0.1") + Decimal("0.2")` → `Decimal('0.3')` | 税率・利率などの計算 |
| データベースの `DECIMAL` / `NUMERIC` 型 | `price NUMERIC(10, 2)` | 金額の列 |

```python
Decimal("0.1") + Decimal("0.2")   # Decimal('0.3')     ← 文字列から作る
Decimal(0.1)                      # 0.1000000000000000055…  ← float から作るとずれごと入る
```

⚠️ `Decimal(0.1)` のように **float から作ると意味がありません**。必ず文字列 `"0.1"` から作ります。

## 四捨五入も思いどおりにならない

```python
round(2.5)       # 2   ← 3 ではない！
round(3.5)       # 4
round(0.125, 2)  # 0.12
```

```javascript
Math.round(2.5)      // 3
Math.round(-2.5)     // -2
(1.005).toFixed(2)   // "1.00"  ← 1.01 ではない
```

（すべて実行して確認した結果です）

| 何が起きているか | 説明 |
|---|---|
| Python の `round(2.5)` が 2 | 「ちょうど半分なら偶数のほうへ丸める」方式（銀行家の丸め）。誤差がたまりにくい |
| `(1.005).toFixed(2)` が `"1.00"` | 1.005 が実際には 1.00499999… として覚えられているため |
| JavaScript の `Math.round(-2.5)` が -2 | 「大きいほうへ」丸めるので、マイナスでは 0 に近づく |

学校で習う「四捨五入」が必要なら、Python では `Decimal` の `quantize(..., rounding=ROUND_HALF_UP)` を使います。
**税込み価格の計算など、1 円のずれが問題になる場面** では、AI のコードがどの丸め方を使っているかを必ず確認しましょう。

## 整数の大きさ：Python は無限、JavaScript は限界あり

```python
print(2 ** 64)     # 18446744073709551616   Python の整数はいくらでも大きくできる
```

```javascript
console.log(Number.MAX_SAFE_INTEGER)   // 9007199254740991（約 9000 兆）
console.log(9007199254740993)          // 9007199254740992  ← 1 ずれた！
console.log(9007199254740993n)         // 9007199254740993n ← BigInt なら正確
```

JavaScript の普通の数（`Number`）は、中身が小数（float）なので、約 9000 兆を超えると **整数でもずれます**。

⚠️ これが実際に問題になるのは **ID** です。X（旧 Twitter）や Discord の ID は 19 桁ほどあり、JSON の数値のまま JavaScript で読むと、下の桁が変わって別の ID になります。そのため、多くの API は ID を **文字列** `"1234567890123456789"` で返します。

## AI のコードではこう出てくる

| 見かけたら | チェック |
|---|---|
| `price * 1.1` で税込み計算 | ⚠️ 誤差と丸め方。整数や `Decimal` にしているか |
| `if total == 0.3:` | ⚠️ 小数を `==` で比べている。`math.isclose` か整数に |
| `round(x)` で四捨五入のつもり | ⚠️ Python は偶数への丸め。必要なら `ROUND_HALF_UP` |
| JavaScript で `JSON.parse` した大きな ID | ⚠️ 数値のままだとずれる。文字列で受け取っているか |
| `Decimal("19.99")` / 金額を整数のセントで保存 | ✅ |

```quiz
? Python で `0.1 + 0.2 == 0.3` が `False` になる理由は？
- Python のバグ
+ 2 進数では 0.1 などを正確に表せず、わずかな誤差があるから
- 足し算の順番が決まっていないから
> 0.1 は 2 進数で無限に続く小数になるため、決まった桁数で切ったずれた値を覚えています。ほぼすべての言語で同じです。

? お金の計算の方法として適切なのは？
- `float` で計算し、最後に `round` する
+ 円やセントの整数で持つか、文字列から作った `Decimal` を使う
- `Decimal(0.1)` のように float から Decimal を作る
> 整数で持てば誤差はありません。Decimal は必ず文字列から作ります（float から作ると誤差ごと入ります）。

? JavaScript で 19 桁の ID を数値のまま扱うと、何が起きうる？
- 自動で BigInt に変換される
- エラーで止まる
+ エラーは出ずに、下の桁が変わって別の値になる
> 約 9000 兆（`Number.MAX_SAFE_INTEGER`）を超えると整数でも正確に表せません。エラーが出ないので気づきにくいのが怖いところです。
```
