## このレッスンのゴール

- 開発環境と本番環境の違いを説明できる
- Dockerfile を読んで、何をしているか分かる
- ホスティングの種類（PaaS・サーバーレス・VPS・BaaS）を見分けられる
- デプロイの前後に確認すべきことが分かる

## 「手元で動いた」から「みんなが使える」へ

`localhost:8000`（レッスン 2）は自分のパソコンの中だけ。みんなに使ってもらうには、**インターネットにつながったサーバーで動かす** 必要があります。これを **デプロイ**（配置）と呼びます。

| | 開発環境 | 本番環境 |
|---|---|---|
| どこで | 自分のパソコン | クラウドのサーバー |
| データベース | SQLite・使い捨て | PostgreSQL など・**本物のデータ** |
| 秘密情報 | `.env` | クラウドのシークレット管理 |
| エラー表示 | 詳しく出す | 利用者には最小限、詳細はログへ |
| `--reload` | 付ける | 付けない |

## 設定は環境変数で切り替える

同じコードを、開発でも本番でも動かせるように、**違いは全部「環境変数」で渡します**（AI と開発するコース「秘密情報と環境変数」）。

```python
import os
DATABASE_URL = os.environ["DATABASE_URL"]       # 開発：sqlite:///app.db  本番：postgresql://...
SECRET_KEY = os.environ["SECRET_KEY"]
DEBUG = os.environ.get("DEBUG") == "1"
```

コードの中に「本番ならこうする」と書き分けないのがコツです。

## Docker：動く環境ごと箱に詰める

「私のパソコンでは動いたのに、サーバーでは動かない」の多くは、Python のバージョンやライブラリの違いが原因です。
**Docker** は、アプリと、それが動く環境（OS・Python・ライブラリ）を **1 つの箱（コンテナ）** に詰めて、どこでも同じように動かす道具です。

```dockerfile
FROM python:3.12-slim                         # ① 土台：Python 3.12 が入った小さな Linux
WORKDIR /app                                  # ② 作業フォルダ
COPY requirements.txt .                       # ③ ライブラリの一覧を先にコピーして
RUN pip install --no-cache-dir -r requirements.txt   #    インストール
COPY . .                                      # ④ アプリのコードをコピー
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]   # ⑤ 起動コマンド
```

| 命令 | 意味 |
|---|---|
| `FROM` | どの箱を土台にするか |
| `WORKDIR` | 以降の作業をするフォルダ |
| `COPY` | パソコンのファイルを箱の中へ |
| `RUN` | 箱を作るときに 1 回だけ実行するコマンド |
| `CMD` | 箱を起動したときに実行するコマンド |

- `--host 0.0.0.0`：箱の **外から** のアクセスを受け付ける（`127.0.0.1` だと箱の中からしか届かない）
- ③ で先に requirements.txt だけコピーするのは、コードを変えただけのときに、インストールをやり直さずに済ませる工夫（Docker はステップごとに結果を覚えている）

## ホスティングの種類

| 種類 | 例 | 自分で面倒を見る範囲 | 向いている場面 |
|---|---|---|---|
| **BaaS** | Firebase、Supabase | ほぼ無し（ルールの設定くらい） | 小さなアプリ・試作（popup2027） |
| **PaaS** | Render、Railway、Fly.io、Google Cloud Run | コード（や Docker）を渡すだけ | 個人〜中規模の Web API |
| **サーバーレス関数** | AWS Lambda、Cloudflare Workers、Vercel Functions | 関数だけ | アクセスが少ない・波がある API |
| **VPS / 仮想マシン** | EC2、さくらの VPS | OS の更新・セキュリティまで全部 | 細かく制御したい |

**初めてなら、BaaS か PaaS がおすすめ** です。サーバーの OS の更新やセキュリティ対策を、サービス側が引き受けてくれます。

サーバーレス関数の例として、Cloudflare Workers と、そこから使えるデータベース D1 をレッスン 19 で実際に動かします。

## CI/CD：テストして、自動で出す

```text
push → テスト（CI、レッスン 12）→ 合格したら自動でデプロイ（CD）
```

GitHub Actions で「main に入ったらテストして、通ったら Cloud Run にデプロイ」のように組むのが一般的です。このサイトの「claude/ ブランチを自動で main に取り込む」仕組みも、CI/CD の一種です。

## デプロイのチェックリスト

| いつ | 確認すること |
|---|---|
| 前 | テストが通っている |
| 前 | 環境変数・シークレットが本番に設定されている（**コードに入っていない**） |
| 前 | **マイグレーション**（レッスン 8）でデータが消えないか。**バックアップ** を取った |
| 前 | `DEBUG` が切れている |
| 後 | 主要な API を実際に呼んで確かめる（ヘルスチェック用の `GET /health` を作っておくと便利） |
| 後 | エラー監視・ログに異常が出ていない（レッスン 10） |
| いざというとき | **前の版に戻す方法**（ロールバック）を知っている |

```quiz
? 開発と本番で、データベースの接続先を切り替えるよい方法は？
- コードの中で if 本番: と書き分ける
+ 環境変数 DATABASE_URL で渡す
- 本番用のファイルを別に作ってコピーする
> 同じコードのまま、外から渡す設定だけを変えるのが基本です。

? Dockerfile の `CMD` の役割は？
- 箱を作るときにライブラリをインストールする
+ 箱を起動したときに実行するコマンドを決める
- ファイルをコピーする
> RUN は作るときに 1 回、CMD は起動するたびに実行されます。

? デプロイ前に特に気をつけたいことは？
+ マイグレーションでデータが消えないか確認し、バックアップを取る
- コードのコメントを全部消す
- テストを消して速くする
> 本番のデータは取り返しがつかないので、必ず確認とバックアップを。
```
