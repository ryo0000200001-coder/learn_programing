## このレッスンのゴール

- N+1 問題を見つけて、直し方を説明できる
- インデックスが何をしているか説明できる
- キャッシュの使いどころと注意点が分かる
- 「まず測る」を習慣にできる

## まず測る

「遅い気がする」で直し始めると、関係ない所をいじりがちです。

- どの API が遅いか（ログに処理時間を出す。レッスン 10）
- その API の中で、何に時間がかかっているか（データベース？ 外部 API？ 計算？）

バックエンドが遅い原因は、多くの場合 **データベースへの問い合わせ** です。次の 2 つがその代表です。

## ① N+1 問題

タスク一覧を、担当者の名前つきで返す API を考えます（レッスン 8 のモデル）。

```python
tasks = session.scalars(select(Task)).all()          # ① タスクを全部取る：1 回
return [{"title": t.title, "assignee": t.assignee.name} for t in tasks]
                                                       # ② t.assignee のたびに 1 回ずつ問い合わせ
```

`t.assignee` は、**たどった瞬間にデータベースへ聞きに行く**（遅延読み込み）ので、タスクが 50 件あると、

```text
1 回（タスク一覧）＋ 50 回（担当者を 1 人ずつ）＝ 51 回
```

の問い合わせになります。これが **N+1 問題** です（実際に数えて 51 回でした）。件数が増えるほど、どんどん遅くなります。

**直し方**：最初に「担当者もまとめて取ってきて」と頼みます。

```python
from sqlalchemy.orm import selectinload

tasks = session.scalars(select(Task).options(selectinload(Task.assignee))).all()
```

これで問い合わせは **2 回**（タスク一覧 ＋ 担当者をまとめて 1 回）になりました（実測）。

| ORM | まとめて取る書き方 |
|---|---|
| SQLAlchemy | `selectinload(...)` / `joinedload(...)` |
| Django | `select_related(...)` / `prefetch_related(...)` |
| Prisma | `include: { assignee: true }` |
| Rails | `includes(:assignee)` |

**見つけ方**：開発中に SQL のログを出す（SQLAlchemy なら `create_engine(..., echo=True)`）。同じ形の SELECT がずらっと並んでいたら N+1 です。
**AI のコードで、ループの中で関連データをたどっていたら要注意** です。

## ② インデックスが無い

```sql
SELECT count(*) FROM tasks WHERE owner_id = ?
```

インデックスが無いと、データベースは **表を最初から最後まで全部見て** 探します。本の中から言葉を探すのに、1 ページ目から全部めくるようなものです。

**インデックス** は本の **索引** です。「owner_id が 5 の行はここ」という一覧を別に作っておき、すぐに見つけられるようにします。

```sql
CREATE INDEX idx_tasks_owner ON tasks(owner_id);
```

100 万行のテーブルで実際に測ると、こうなりました（このパソコンでの例）。

| | 調べ方（EXPLAIN の結果） | 1 回あたり |
|---|---|---|
| インデックス無し | `SCAN tasks`（全部見る） | 約 22 ms |
| インデックスあり | `SEARCH tasks USING ... INDEX`（索引で探す） | 約 0.02 ms |

**約 1,000 倍** 速くなりました。

- **`WHERE`・`ORDER BY`・`JOIN` によく使う列** にインデックスを付ける
- 主キーには最初から付いている
- 付けすぎると、追加・更新のたびに索引の更新が必要になり、書き込みが遅くなる
- `EXPLAIN`（PostgreSQL なら `EXPLAIN ANALYZE`）で、インデックスが使われているか確かめられる

## ③ キャッシュ：同じ答えを使い回す

「何度聞かれても、しばらくは同じ答え」のものは、**一度計算した結果をとっておいて使い回す** と速くなります。これがキャッシュです。

| 置き場所 | 例 |
|---|---|
| ブラウザ | `Cache-Control: max-age=3600`（1 時間は再取得しない） |
| CDN（世界中にある配信用サーバー） | 画像・CSS・JavaScript・公開ページ |
| サーバーのメモリ・**Redis** | ランキング、外部 API の結果、重い集計 |

```python
def get_weather(city: str):
    cached = redis.get(f"weather:{city}")
    if cached:
        return json.loads(cached)                          # あればそれを返す
    data = call_weather_api(city)                          # 無ければ取ってきて
    redis.set(f"weather:{city}", json.dumps(data), ex=600) # 10 分とっておく
    return data
```

### キャッシュの難しさ

> コンピュータサイエンスで難しいことは 2 つだけ。キャッシュの無効化と、名前付けだ。（よく引用される言葉）

- **古い情報が出る**：元のデータが変わったのに、キャッシュの古い答えが返る。**期限（`ex=600`）を必ず付ける**、更新したらキャッシュを消す
- **人によって違うものをキャッシュしない**：ログインした人ごとのデータを全員共通のキャッシュに入れると、**他人の情報が見えてしまう** 事故になる

## その他の定番

| 対策 | 内容 |
|---|---|
| ページ分け | 一覧を全件返さない（レッスン 4） |
| 必要な列だけ取る | `SELECT *` ではなく、使う列だけ |
| 重い仕事は裏へ | レッスン 13 |
| 接続の使い回し | データベースへの接続を毎回作らず、プール（ためておく仕組み）で使い回す。多くのフレームワークや ORM が自動でやってくれる |

```quiz
? タスク 100 件を取って、ループの中で `task.assignee.name` をたどると、問い合わせは何回になりやすい？
- 1 回
- 2 回
+ 101 回
> 一覧 1 回＋担当者を 1 件ずつ 100 回。N+1 問題です。selectinload などでまとめて取ります。

? インデックスを付けると速くなるのはどんな問い合わせ？
+ その列で WHERE や ORDER BY をする問い合わせ
- すべての INSERT
- テーブルの削除
> 索引で目的の行をすぐ見つけられるようになります。書き込みは少し遅くなります。

? キャッシュで特に避けるべきことは？
- 期限を付けること
+ ログインした人ごとのデータを、全員共通のキャッシュに入れること
- 外部 API の結果を入れること
> 他人の情報が見えてしまう事故につながります。
```
