## このレッスンのゴール

- 「ステートレスにする」と、なぜサーバーを増やせるのか説明できる
- コードを層（ルーター・サービス・リポジトリ）に分ける理由が分かる
- モノリスとマイクロサービスの違いと、選び方の考え方を説明できる

## 利用者が増えたらどうする？

| 方法 | 内容 | たとえ |
|---|---|---|
| **垂直スケール** | サーバーを強くする（CPU・メモリを増やす） | 料理人を腕のいい人に替える |
| **水平スケール** | サーバーの台数を増やす | 料理人を何人も雇う |

垂直スケールは簡単ですが、限界があります。大きなサービスは **水平スケール** で伸びていきます。

```text
               ┌─▶ サーバー A ─┐
利用者 ─▶ ロードバランサー ─┼─▶ サーバー B ─┼─▶ データベース
               └─▶ サーバー C ─┘
```

**ロードバランサー** が、届いたリクエストを空いているサーバーに振り分けます。

## ステートレス：どのサーバーに来てもよい作り

水平スケールの前提は、**どのサーバーにリクエストが来ても同じように処理できる** ことです。

```python
# ❌ サーバーのメモリにログイン状態やデータを持つ
sessions = {}          # サーバー A で覚えても、次のリクエストがサーバー B に行くと「知らない人」
tasks = {}             # レッスン 5 の辞書。サーバーごとに中身がバラバラになる
```

```text
⭕ 状態はサーバーの外に置く
  - データ          → データベース
  - ログイン状態    → JWT（毎回持ってきてもらう）か、Redis などの共有の置き場所
  - アップロードされたファイル → ファイル置き場（S3・Cloud Storage など）
```

サーバー自身は何も覚えていない（**ステートレス**）ので、台数を増やしても減らしても大丈夫になります。
レッスン 3 の「HTTP は覚えていない」と同じ考え方を、サーバーにも当てはめるわけです。

## コードを層に分ける

AI が書く中〜大規模のバックエンドは、よくこういうフォルダ構成になっています。

```text
app/
├── main.py            アプリの組み立て（ルーターの取り付け・設定）
├── routers/           ① 窓口：HTTP の受け取りと返事（ステータス・検証）
│   └── tasks.py
├── services/          ② 業務のルール：「締め切りは本番より前」「完了したら通知」
│   └── task_service.py
├── repositories/      ③ データの出し入れ：SQL・ORM はここだけ
│   └── task_repo.py
├── models.py          テーブルの定義（ORM）
└── schemas.py         入出力の型紙（Pydantic）
```

| 層 | 知っていること | 知らなくていいこと |
|---|---|---|
| ① ルーター | HTTP（URL・ステータス） | SQL |
| ② サービス | 業務のルール | HTTP・SQL |
| ③ リポジトリ | データベース | HTTP |

こう分けると、

- 「データベースを PostgreSQL から別のものに替える」→ ③ だけ直せばよい
- 「同じルールを、API からも定時の処理（レッスン 13）からも使う」→ ② を呼べばよい
- テストで ③ を偽物に差し替えて、② のルールだけを確かめられる

fashion_news で「notion.py だけ取り替えれば LINE に送れる」、popup2027 で「store が保存先の違いを隠している」と話したのも、同じ **役割を分けて、境目をはっきりさせる** 考え方です。

**AI のバックエンドを読むときは、まずこのフォルダ構成を見て、「どの層の話か」を意識すると迷子になりません**（レッスン 17）。

## モノリスとマイクロサービス

| | モノリス | マイクロサービス |
|---|---|---|
| 形 | 1 つのアプリにすべての機能 | 機能ごとに別々のアプリ（ユーザー・注文・決済…）が API で話す |
| 良い点 | 作りやすい・テストしやすい・速い | 機能ごとに別のチームが別々に開発・デプロイ・スケールできる |
| 悪い点 | 大きくなると、ちょっとした変更でも全体に影響しやすい | 通信の失敗・データの食い違い・運用の手間が一気に増える |
| 向いている | **ほとんどの小〜中規模のサービス** | 何十人・何百人の開発者がいる大きな組織 |

**最初はモノリスで、層をきれいに分けて作る** のが、今の多くの現場での定石です。「マイクロサービスにしましょう」と AI が提案してきたら、本当にその規模か考えましょう。

## 規模に合った作りを選ぶ

| 規模 | 例 | 作り |
|---|---|---|
| 自分・数人 | popup2027、fashion_news | BaaS（Firebase）や、GitHub Actions の定時処理で十分 |
| 〜数千人 | 小さな Web サービス | PaaS ＋ モノリス ＋ PostgreSQL |
| それ以上 | 大きなサービス | 水平スケール・キャッシュ・ジョブキュー・必要に応じてサービス分割 |

**大は小を兼ねません**。小さなアプリに大きな仕組みを入れると、作るのも直すのも大変になります。AI は頼まれると立派な構成を作りがちなので、「今の規模にこれは必要？」と聞き返すのも大事な仕事です。

```quiz
? サーバーを 3 台に増やしたら、ログインしたのに「ログインしていません」と言われることがある。原因として考えられるのは？
+ ログイン状態を各サーバーのメモリに持っていて、別のサーバーにリクエストが届いた
- ロードバランサーが無いから
- データベースが遅いから
> 状態をサーバーの外（JWT・Redis など）に置き、ステートレスにします。

? 「SQL を書いてよいのはリポジトリ層だけ」にしておくと、何がうれしい？
- 処理が必ず速くなる
+ データベースを替えるときに、直す場所が 1 か所にまとまる
- SQL インジェクションが起きなくなる
> 役割を分けておくと、変更の影響が狭い範囲に収まります。

? 3 人で使う予定の小さなアプリを作るとき、まず選ぶのに合う作りは？
+ BaaS やモノリスなど、シンプルな構成
- 機能ごとに 10 個のマイクロサービス
- サーバーを 100 台用意する
> 規模に合わない大きな構成は、作るのも直すのも大変になります。
```
