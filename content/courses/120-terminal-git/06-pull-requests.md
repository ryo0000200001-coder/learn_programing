## このレッスンのゴール

- プルリクエストの流れ（ブランチ → push → PR → レビュー → マージ）を説明できる
- PR の画面（Files changed・Checks・Conversation）で何を見ればよいか分かる
- マージの 3 つの方法（Merge・Squash・Rebase）の違いが分かる

## プルリクエストとは

**プルリクエスト（PR）** は、「このブランチの変更を main に取り込んでください」という **提案** です。GitHub 上で、変更の中身を見ながら話し合い、OK になったらマージします。
GitLab では **マージリクエスト（MR）** と呼びますが、同じものです。

```text
① ブランチを作って作業・コミット（レッスン 4）
② git push -u origin ブランチ名
③ GitHub で PR を作る（タイトルと説明を書く）
④ 自動テスト（CI）が走る ＋ 人がレビューする
⑤ 指摘があれば、同じブランチに追加でコミットして push（PR に自動で反映）
⑥ OK になったら「Merge」ボタン → main に入る
⑦ ブランチを消す
```

AI のエージェント（Claude Code など）に作業を任せるときも、**PR にしてもらってから、自分で確認してマージする** のが安全な進め方です（AI と開発するコースの「エージェントに任せるときの進め方」）。

## PR の作り方

push すると、GitHub の画面に「Compare & pull request」ボタンが出ます。コマンドで作るなら GitHub CLI（`gh`）を使います。

```bash
gh pr create --title "Add banana to shopping list" --body "バナナが売り切れていたので次回用に追加"
gh pr list                 # PR の一覧
gh pr view 12              # 12 番の PR の内容
gh pr checkout 12          # 12 番の PR のブランチを手元に持ってきて試す
gh pr merge 12 --squash    # 12 番を Squash でマージ
```

### よい PR の説明

| 書くこと | 例 |
|---|---|
| 何を変えたか | 税込み価格の計算を `Decimal` に変更 |
| なぜ変えたか | 8% の商品で 1 円ずれる不具合があったため（Issue #34） |
| どう確かめたか | 単体テストを追加。198 円 × 3 個 = 641 円になることを確認 |
| 見てほしいところ | 端数の切り捨て・四捨五入の方針がこれでよいか |

## PR の画面の読み方

| タブ | 何がある | 見ること |
|---|---|---|
| **Conversation** | 説明・コメント・レビューの結果・マージボタン | 何のための変更か。未解決の指摘が残っていないか |
| **Commits** | この PR に含まれるコミットの一覧 | 関係ない変更が混ざっていないか |
| **Checks** | 自動テスト（GitHub Actions など）の結果 | ✅ 緑なら合格、❌ 赤なら失敗。赤のままマージしない |
| **Files changed** | 変更の差分（レッスン 3 の diff） | ここが本体。1 行ずつ読む |

Files changed では、行番号の横の **「+」を押すとその行にコメント** が付けられます。最後に「Review changes」から次のどれかを選びます。

| 選択 | 意味 |
|---|---|
| **Comment** | 感想・質問だけ |
| **Approve** | OK。マージしてよい |
| **Request changes** | 直してほしいところがある。直るまでマージしない |

## レビューで見ること

AI と開発するコースの「差分を読む」のチェックリストに、PR ならではの点を足すと次のようになります。

| 観点 | 質問 |
|---|---|
| 目的 | 説明に書いてあることと、差分が一致しているか。**頼んでいない変更** が混ざっていないか |
| 大きさ | 大きすぎないか（目安：数百行を超えたら分けてもらう） |
| テスト | 変更に合わせてテストが追加・更新されているか。Checks は緑か |
| 秘密情報 | `.env`、API キー、パスワードが入っていないか |
| 消えたもの | 削除された行（赤）に、必要な処理が含まれていないか |
| 依存関係 | `requirements.txt`・`package.json` に知らないライブラリが増えていないか（セキュリティのコース） |

AI が作った PR は、説明が立派でも **実際の差分と一致しているとは限りません**。説明ではなく、Files changed を基準に確認しましょう。

## マージの 3 つの方法

| ボタン | 何が起きるか | 履歴 |
|---|---|---|
| **Create a merge commit** | マージコミットを作る（レッスン 4 の ②） | ブランチのコミットがすべて残り、分かれて合流する形 |
| **Squash and merge** | PR のコミットを **1 つにまとめて** main に入れる | main は 1 PR ＝ 1 コミットの、まっすぐな履歴 |
| **Rebase and merge** | PR のコミットを、main の先頭に 1 つずつ付け直す | まっすぐな履歴。コミットは個別に残る |

「修正」「typo」「やっぱり戻す」のような細かいコミットがたくさんある PR は、**Squash** にすると main の履歴が読みやすくなります。どれを使うかはチームで決めておきます。

## このリポジトリの場合

このサイトでは、利用者の了承のもとで **PR を省略** しています。

```yaml
on:
  push:
    branches: ["claude/**"]     # claude/ で始まるブランチに push されたら
...
      git merge --no-edit "origin/${GITHUB_REF_NAME}"   # main にマージして
      git push origin main                               # main を push する
```

`.github/workflows/auto-merge-claude.yml` の一部です。学習用の自分だけのサイトなので、毎回の確認の手間を省いています。
チームの開発や、お金・個人情報を扱うアプリでは、このような自動マージではなく、**PR で人が確認してからマージする** のが基本です。

```quiz
? プルリクエストを作った後で修正を頼まれた。どうすれば PR に反映される？
- 新しい PR を作り直す
+ 同じブランチに修正をコミットして push する
- main に直接 push する
> PR はブランチにひもづいているので、同じブランチに push すれば自動で反映されます。

? AI が作った PR のレビューで、いちばん信用してよい情報は？
- PR の説明文
- コミットメッセージ
+ Files changed の実際の差分
> 説明やメッセージは間違っていることがあります。実際に何が変わったかは差分にしか書かれていません。

? 「typo 修正」「やり直し」など細かいコミットが 15 個ある PR を、main の履歴を 1 つにまとめて取り込みたい。選ぶのは？
- Create a merge commit
+ Squash and merge
- Rebase and merge
> Squash は PR のコミットを 1 つにまとめます。main の履歴が「1 PR ＝ 1 コミット」になって読みやすくなります。
```
