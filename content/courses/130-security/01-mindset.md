## このレッスンのゴール

- 「信頼の境界線」の意味を説明し、コードの中で外から来るデータを見つけられる
- 守るべき 3 つのもの（機密性・完全性・可用性）を、例で説明できる
- 最小権限・多層防御という考え方を知り、AI のコードの判断に使える

## 攻撃者は「想定外の使い方」をする

普通の利用者は、名前の欄に名前を、数量の欄に 1〜10 くらいの数を入れます。攻撃者はそうしません。

| 入力欄 | 普通の人 | 攻撃者が試すこと |
|---|---|---|
| 名前 | `Ryo` | `' OR '1'='1`（レッスン 3）、`<script>...</script>`（レッスン 4） |
| 数量 | `2` | `-100`、`99999999999`、`2.5`、`"abc"` |
| URL の ID | `/orders/15` | `/orders/16`（他人の注文、バックエンドコースの IDOR） |
| ファイル | `photo.jpg` | 中身がプログラムの `photo.jpg`、10GB のファイル、`../../.env` という名前 |
| ログイン | 正しいパスワードを 1 回 | よくあるパスワードを 1 秒に何千回 |

**セキュリティとは、「想定外の使い方をされても、困ったことにならない」ようにすること** です。

## 信頼の境界線

プログラムの中で、**自分がコントロールしていないところから来るデータ** は、すべて攻撃者が自由に作れると考えます。

```text
         信頼できない（外）          │        信頼できる（中）
                                    │
  ブラウザから送られる値 ─────────→ │ → チェック → 自分のサーバーのコード
  URL・フォーム・JSON・Cookie       │                    ↓
  アップロードされたファイル         │               データベース
  他社の API の返事                  │
  AI（LLM）の出力                    │
```

| 「外」から来るもの | 例 |
|---|---|
| リクエストのすべて | URL・クエリ・フォーム・JSON の本文・ヘッダー・Cookie |
| ブラウザ側のチェック | JavaScript の入力チェックは **飛ばせる**（直接リクエストを送ればよい） |
| ファイル名・ファイルの中身 | 拡張子は名札にすぎない（コンピュータの基礎コース） |
| 外部の API・Web ページ | 改ざん・乗っ取りの可能性 |
| **LLM の出力** | 入力に紛れ込んだ命令に従ってしまうことがある（プロンプトインジェクション） |

⚠️ 特に大事なのは **「ブラウザでチェックしているから大丈夫」は成り立たない** ことです。ブラウザのチェックは使いやすさのため、**守るためのチェックはサーバーで** します。

## 守るべき 3 つのもの

| | 意味 | 破られた例 |
|---|---|---|
| **機密性** | 見てよい人だけが見られる | 他人の住所が見える、パスワードが漏れる |
| **完全性** | 正しい人が、正しいやり方でしか変えられない | 他人の投稿を消せる、値段を書き換えて買える |
| **可用性** | 使いたいときに使える | 大量のリクエストでサーバーが落ちる、データが全部消える |

英語の頭文字で **CIA**（Confidentiality・Integrity・Availability）と呼ばれます。AI のコードを見るときは、「この部分が破られたら、3 つのどれが壊れる？」と考えると、重要度の判断ができます。

## 考え方 1：最小権限

**必要な分だけの権限しか渡さない** という考え方です。

| 場面 | 大きすぎる権限 | 最小権限 |
|---|---|---|
| GitHub のトークン | すべてのリポジトリに書き込める | 1 つのリポジトリの、必要な操作だけ |
| データベースのユーザー | 管理者（テーブルを消せる） | 読み書きだけ |
| OAuth のスコープ | メールも予定表も全部読める | プロフィールだけ（バックエンドコースのレッスン 18） |
| AI のエージェント | 何でも実行してよい | 決めたフォルダの中だけ、危ないコマンドは確認 |

権限が小さければ、**もし漏れたり乗っ取られたりしても、被害が小さく済みます**。

## 考え方 2：多層防御

1 つの対策に頼らず、**何枚も守りを重ねる** 考え方です。どれか 1 枚が破られても、次で止められます。

```text
ブラウザの入力チェック → サーバーのバリデーション → プレースホルダ（SQL）→ データベースの制約 → ログと監視
```

データベース設計のコースで、「アプリでチェックしていても、データベースにも制約を付ける」と学んだのも、この考え方です。

## 考え方 3：秘密は「隠し場所」ではなく「鍵」で守る

「URL を知っている人しか見られないから安全」「分かりにくい名前のフォルダに置いたから安全」は、**隠しているだけ** で、守っていません。URL は履歴・共有・ログから漏れます。
本当に守るなら、**ログインして権限を確かめる** 仕組みにします。

## AI のコードではこう出てくる

AI のコードを読むときは、次の順番で見ていきます。このコースのレッスンが、それぞれの詳しい説明です。

| 順番 | 見ること | レッスン |
|---|---|---|
| ① | 外から来るデータはどこから入る？（`request.`、`input()`、`req.body`、ファイル） | このレッスン |
| ② | それは SQL・HTML・コマンド・ファイルパスに **そのまま** 使われていないか | 3・4 |
| ③ | パスワード・トークン・秘密の扱いは正しいか | 2・5 |
| ④ | 「誰が」「何を」してよいかを、サーバーで確かめているか | 5 |
| ⑤ | 使っているライブラリは安全か | 6 |

```quiz
? ブラウザの JavaScript で「数量は 1〜10」とチェックしている。サーバー側のチェックは必要？
- 不要。ブラウザでチェックしているので、おかしな値は送られてこない
+ 必要。攻撃者はブラウザを使わずに、好きな値のリクエストを直接送れる
- 必要だが、数量のような小さなことには不要
> ブラウザのチェックは使いやすさのためのもので、飛ばせます。守るためのチェックは必ずサーバーで行います。

? 「最小権限」の例として正しいのは？
- 開発を楽にするため、トークンには全部の権限を付けておく
+ リポジトリに保存するだけのトークンは、そのリポジトリの書き込み権限だけにする
- 管理者のアカウントを全員で共有する
> 必要な分だけの権限にしておけば、漏れたときの被害が小さくなります。

? 「URL を知っている人しか見られないので、ログインは不要」という設計の問題は？
+ URL は履歴・共有・ログなどから漏れるので、隠しているだけで守れていない
- URL が長くなりすぎる
- 問題はない
> 推測しにくい URL は補助にはなりますが、守りにはなりません。見てよい人かどうかを確かめる仕組みが必要です。
```
